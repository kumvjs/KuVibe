# Project Schema 1 → 2

## Purpose

Adopt projects created before KuVibe had explicit version state. Schema 2 introduces `.agents/kuvibe.yaml`, managed template metadata, and a bounded KuVibe router block without changing the project's accumulated knowledge.

Schema 1 is implicit: the state file is absent and at least one legacy harness marker exists (`AGENTS.md`, `.agents/project.md`, or `.agents/context/stack.md`). An empty/uninitialized project is not schema 1.

## Preconditions

- The active `kuVibe.md` declares schema 2 and supports schema 1.
- `.agents/kuvibe.yaml` does not exist.
- At least one legacy harness marker exists.
- Relevant Git status and diffs have been inspected when Git is available.

If existing metadata is malformed, do not classify it as schema 1 and do not overwrite it.

## Add

- `.agents/kuvibe.yaml` using the schema 2 state contract.
- A bounded `agents-router` managed block in `AGENTS.md`.
- Managed metadata on workflows that the migration can safely classify.

## Merge

- Add version checking before normal requirement intake.
- Preserve customized workflow instructions and merge current protocol requirements into them.
- Preserve all content outside the `AGENTS.md` managed block.

If an artifact matches a known unmodified KuVibe template, it may adopt the current template and revision. If it differs or provenance is uncertain, classify it as mixed and do not replace its body.

## Preserve

- `.agents/project.md`
- `.agents/context/**` project facts and custom rules
- `.agents/notes/**` including every historical note body
- `docs/**` project and business content
- User instructions outside managed blocks
- Unrelated repository files and uncommitted changes

## Deprecate and Remove

None. This transition is additive. Do not delete legacy artifacts merely because the current template set does not contain them.

## Validation

- The candidate `.agents/kuvibe.yaml` content contains valid SemVer `0.2.0`, integer schema `2`, timestamps, and applied template revisions.
- `AGENTS.md` has exactly one balanced `agents-router` managed block and still contains prior project-specific instructions.
- Required context and workflow files are readable.
- Requirement routing performs version checking before normal work.
- Project-owned docs and historical notes are unchanged.
- References do not point to removed files; this migration removes none.

## Commit State Last

Validate the candidate state before committing it. Write a timestamped `migration` note, write `.agents/kuvibe.yaml` last, then run final read-only validation. If any pre-commit validation fails, report the completed and pending steps and do not claim schema 2. If final validation fails, report the inconsistent state immediately and do not continue to another migration.
